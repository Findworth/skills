# 外包项目评估 Skill（outsourcing-evaluation）

## 这个 skill 是什么

一套用于产品团队判断"这个外包项目接不接"的评估框架。在产品团队与对方确认需求边界后使用，覆盖 **6 个评估维度 + 4 条否决红线 + 4 种决策结论**，目标是避免凭感觉决策，尽可能给出明确、可追溯的判断

---

## 决策流程

```
对方需求边界已确认？
  │
  ├── 否 → 先对齐需求边界，再来评估
  │
  └── 是 → 检查红线
              │
              ├── 触发红线 → ❌ 不接（直接输出，不走后续流程）
              │
              └── 未触发 → 逐维评估（6 维）
                              │
                              ├── 关键信息缺失 → 🔄 需更多信息
                              ├── 全部可接受 → ✅ 接
                              ├── 多数可接受，1-2 维有前置条件 → ⚠️ 有条件接
                              └── 多维度不可接受 → ❌ 不接
```

---

## 红线（自动否决，触发任一条直接输出 ❌ 不接）

以下 4 条是硬 veto，不需要走完 6 维评估即可直接下结论：

| # | 红线 | 说明 |
|---|------|------|
| R1 | **付款条件不可接受** | 如全款在交付后支付、账期超过公司承受能力、无预付款/里程碑付款 |
| R2 | **触及合规/法律/版权红线** | 涉及灰色地带、数据来源不合法、知识产权归属不清、出口管制等 |
| R3 | **核心人员不可替代且无法排期** | 项目强依赖某个不可替代的人，而该人员已满负荷或无意愿参与 |
| R4 | **需求完全不可定义** | 对方说不清要做什么，且经过两轮需求对齐后仍然无法明确边界 |

---

## 6 维评估框架

每维 4-6 个确认项。评估时逐项判断：✅ 可接受 / ⚠️ 有风险但可解决 / ❌ 不可接受。

### 维度 1：技术可行性与技术资源

**核心问题**：现有团队有没有能力做？如果不能，有没有可行的替代方案？

| # | 确认项 | 说明 |
|---|--------|------|
| 1.1 | 核心功能是否可以基于现有技术栈实现？ | 是否需要引入全新语言/框架/基础设施？引入成本是否可接受？ |
| 1.2 | 是否存在技术不确定性需要提前验证？ | 有没有没做过的事情？是否需要 PoC 或技术预研？验证周期多长？ |
| 1.3 | 是否需要采购/接入第三方服务？ | 如云服务、API、SDK、字体/图片授权等。成本和时间是否可接受？ |
| 1.4 | 技术总成本估算是否在可接受范围？ | 包括人力 + 第三方服务 + 基础设施 + license 等 |

### 维度 2：团队资源与排期匹配度

**核心问题**：有没有足够的人和 time slot？会不会挤占主线产品？

| # | 确认项 | 说明 |
|---|--------|------|
| 2.1 | 项目是否会挤占已承诺的主线工作？ | 排期是否与现有 milestone 冲突？是否需要推迟已确定的发布？ |
| 2.2 | 产品/设计/开发分别需要多少投入？ | 每个角色需要多少人、多长时间？是否都有可用人员？ |
| 2.3 | 对方期望的周期是否与团队实际排期匹配？ | 如果日期不可谈，团队能否在期限内高质量交付？ |
| 2.4 | 是否存在关键人员不可替代的问题？ | 某个人是唯一能做某事的，ta 离职/生病项目就停摆？（同时检查红线 R3） |
| 2.5 | 项目结束后人员如何安置？ | 是临时借调还是长期投入？项目结束后人员能否顺利回归主线？ |

### 维度 3：需求成熟度与交付可控性

**核心问题**：对方有没有想清楚？边界能不能定义清楚？交付能不能可控？

| # | 确认项 | 说明 |
|---|--------|------|
| 3.1 | 对方是否能清晰描述要做什么？ | 有没有 PRD/需求文档/原型？还是只有口头描述？ |
| 3.2 | 做什么/不做什么是否已明确定义？ | 需求边界清晰吗？有没有"画一条线"说线外的不做？ |
| 3.3 | 当前阶段的开发范围是否已有良好定义？ | 第一期做什么是否明确？还是"先做着再说"？ |
| 3.4 | 是否存在未解决的依赖会阻塞后续工作？ | 如依赖第三方接口还没拿到文档、依赖对方提供素材/内容、依赖审批流程等 |
| 3.5 | 验收标准和交付物是否有共识？ | 什么算"做完"？以什么标准验收？谁来验收？验收周期多长？ |

### 维度 4：主线产品契合度

**核心问题**：这个项目和我们的主线产品有没有关系？能不能互相借力？

| # | 确认项 | 说明 |
|---|--------|------|
| 4.1 | 项目和主线产品在功能上有没有相似/可复用的部分？ | 组件/模块/服务能不能直接复用或稍作改造？评估复用比例 |
| 4.2 | 项目积累的经验/技术能不能反哺主线？ | 做完这个项目，主线产品会不会因此变得更好？ |
| 4.3 | 项目会不会把主线带偏方向？ | 定制化需求是否会导致主线架构被污染或技术债累积？ |
| 4.4 | 项目与主线的目标用户/场景有没有交集？ | 能否通过这个项目接触到主线的潜在用户或新场景？ |

### 维度 5：潜在风险评估

**核心问题**：最坏情况是什么？能不能承受？有没有预防或缓解措施？

| # | 确认项 | 说明 |
|---|--------|------|
| 5.1 | 是否存在需求蔓延/范围蠕变的高风险？ | 对方历史上是否经常改需求？合同是否对变更流程有约束？ |
| 5.2 | 是否存在合规、版权、数据安全、舆论风险？ | 数据存储/处理和公司安全策略是否兼容？会不会涉及用户隐私？素材有没有版权问题？项目内容会不会引发舆论争议？（触及红线 R2 则直接否决） |
| 5.3 | 如何定义这个项目的"失败"？ | 交付延期算失败？质量不达标算失败？对方不付款算失败？对方不用算失败？ |
| 5.4 | 项目失败对双方的后果是什么？ | 对我方：经济损失/团队士气/主线影响/客户关系？对对方：业务中断/经济损失？ |
| 5.5 | 对方的决策链路是否清晰？ | 谁说了算？验收谁来拍板？会不会出现"对接人认可但老板推翻"的情况？ |
| 5.6 | 对方过往的外包合作记录如何？ | 有没有拖欠款记录？是否有频繁更换供应商的历史？ |

### 维度 6：商业价值与战略契合

**核心问题**：这个项目从商业上值不值得做？除了赚钱还有没有别的价值？

| # | 确认项 | 说明 |
|---|--------|------|
| 6.1 | 项目收入与利润是否可接受？ | 扣除人力、第三方服务、管理成本后，利润是否达到公司基准线？ |
| 6.2 | 付款节奏和现金流是否安全？ | 是否有预付款/里程碑付款？账期多长？如果对方拖欠，最大敞口是多少？ |
| 6.3 | 有没有后续项目或长期合作的可能？ | 这是一次性的还是有机会成为长期客户？如果是长期的，第一期是否愿意接受较低利润？ |
| 6.4 | 客户是否有战略价值？ | 是否是行业标杆客户？是否打开了新行业/新赛道？是否可以作为案例展示？ |
| 6.5 | **机会成本**：不做这个项目，这些人/时间能用来做什么？ | 如果投入主线能产生更大价值，即使外包项目本身不差也应该拒绝 |

## 回答模板

使用本 skill 给出判断时，输出必须包含以下结构：

```
**结论**：[✅ 接 / ⚠️ 有条件接 / 🔄 需更多信息 / ❌ 不接]

**关键依据**（逐维简述，只列有风险或值得注意的维度）：
- 维度 N：[判断，1-2 句]
- ...

**前置条件**（仅 ⚠️ 有条件接 时列出）：
1. [必须在启动前满足的条件]
2. ...

**待确认信息**（仅 🔄 需更多信息 时列出）：
1. [需要补充的关键信息]
2. ...

**主要风险与缓解**（如有不可忽视的风险）：
- 风险：[具体风险描述] → 缓解：[建议措施]
```

## 使用规则

### 1. 红线优先
永远先过一遍 4 条红线。只要触发任意一条，直接输出 ❌ 不接并说明触发了哪条红线。不需要再走 6 维评估。

### 2. 结论先行，依据在后
先给结论，再展开依据。不要让用户看了一大段分析最后还不知道结论是什么。

### 3. 不知道就说不知道
如果关键信息缺失导致无法下结论，输出 🔄 需更多信息，明确列出需要补充的问题，不要硬给结论。

### 4. 有条件接必须列出所有条件
如果结论是 ⚠️ 有条件接，必须把所有前置条件列清楚。条件不满足，结论等价于 ❌。

### 5. 机会成本永远值得问
即使 6 维全部绿灯，也要问一句：这些人/这些时间如果不做这个项目，能做更有价值的事吗？

## 常见误判陷阱

| 陷阱 | 怎么避免 |
|------|---------|
| **因为"关系好"而接** | 个人关系 ≠ 项目可行性。按 6 维走一遍，该拒就拒 |
| **因为"最近没活"而接** | 闲的时候接烂项目，忙的时候更痛苦。机会成本（维度 6.5）要打满 |
| **因为"客户很大"而忽略风险** | 标杆客户 ≠ 无条件接受。大客户的定制需求往往最伤团队。维度 4.3 和 5.1 要重点关注 |
| **因为"技术有趣"而接** | 技术挑战 ≠ 商业价值。新颖技术带来的学习收益放在维度 4.2，不要让它主导决策 |
| **对方说"需求很简单"就信了** | "简单"是最贵的词。用维度 3 逐项确认，要求对方给出具体的范围描述 |
| **忽略验收和付款的衔接** | "做完再验收"≈"做完再扯皮"。维度 5.3 和 6.2 要联动看：验收标准和付款节点是否绑定 |
