# OKR 写作

## 概述

OKR 写作是一个全流程助手，覆盖**制定 → 优化 → 评分复盘**三个场景。核心理念：OKR 不是任务清单，而是"用可验证的结果证据来证明目标已实现"的思考工具。

来源融合：John Doerr《Measure What Matters》+ Google OKR 实践 + 一线团队实战经验（解析法/验证法/场景构建法/打分表设计）。

## 基础概念（三个场景共同前提）

### OKR 是什么

OKR = Objectives（目标）+ Key Results（关键结果）

- **O（目标）**：你想去哪里？→ 定性、鼓舞人心、有方向感
- **KR（关键结果）**：你怎么知道你到了？→ 定量、可衡量、结果导向

一句话：**I will [O] as measured by [KRs]**

### O vs KR vs KPI vs 任务

| 概念 | 本质 | 示例 |
|------|------|------|
| **O** | 你要达成的**状态/结果** | "让用户离不开我们的产品" |
| **KR** | 证明 O 已实现的**可量化证据** | "周活跃用户留存率从 40% 提升至 55%" |
| **KPI** | 日常运营的**健康指标** | "月活跃用户数"（持续监控，但不一定是本季度的突破口） |
| **任务/Task** | 你**做什么**来实现 KR | "重构推荐算法"（是手段，不是结果） |

关键区分：KR 回答的是"做到了会怎样"，不是"要做什么"。

### 承诺型 vs 挑战型 OKR

| 维度 | 承诺型 | 挑战型（Moonshot） |
|------|--------|-------------------|
| 达成期望 | 100% 完成 | 60-70% 即成功 |
| 适用场景 | 必须交付的业务底线 | 探索、突破、创新 |
| 与绩效关系 | 接近 KPI，可能影响考核 | 不与考核挂钩 |
| 设定心态 | "我们必须做到" | "我们试试能不能做到" |

一个团队通常混合使用：核心业务用承诺型，创新探索用挑战型。

### 月度 vs 季度 vs 年度 OKR

这是从一线团队实战中总结的关键差异：

| 维度 | 月度 OKR | 季度 OKR | 年度 OKR |
|------|---------|---------|---------|
| **O 的写法** | 关键词 + 指导方向 + 激励人心 | 关键词 + 指导方向 + 激励人心 | 关键词 + 目标本身（不需额外激励修饰，目标本身足够大就足够激励） |
| **KR 量化** | 可以用打分表处理抽象指标 | 尽量客观量化 | **必须**客观直观量化，**不能用打分表** |
| **KR 粒度** | 可以有阶段性成果 | 适中 | 不能"小气"，必须从高处切入，找跨越全年的锚点 |
| **常见问题** | 手段目标不清晰 | 手段目标不清晰 | 量化小气 + 不确定性（跨时长、业务多、协同团队多） |
| **复盘频率** | 每月 | 每季 | 每半年/每年 |
| **更新灵活度** | 高 | 中 | 低（不宜频繁改，年度内拆成季度 checkpoint） |

**年度 OKR 的特殊挑战——不确定性**：年度 KR 跨一年时间、涉及多块业务、多数需要协同其他团队。制定年度 KR 时需要问自己：**"有哪些量化指标是无论发生什么也要做到的？且这些指标可以支撑起 O？"** 找到这些锚点指标后，其他的不确定性可以在季度 OKR 中动态调整。

## 铁律（任何场景下不可违反）

这 6 条规则是所有 OKR 工作的底线，优化和评估时同样适用：

1. **O 必须定性、鼓舞人心** — 不是"提升用户留存"，而是"让用户离不开我们的产品"。月度 O 需要"关键词 + 指导方向 + 激励人心"三要素，年度 O 目标本身足够大，不需额外修饰激励。
2. **KR 必须定量、结果导向** — 不能写"上线 XX 功能"，必须写"XX 功能上线后，周活跃用户增长 20%"。量化指标要从"代表这个 KR 完成"的角度思考，而非简单堆砌数字。
3. **先 O 后 KR，禁止任务拼凑** — 不能把几个像任务的 KR 凑成一个 O。一定是先想清楚 O，再由 O 推导 KR。O 的结构应该是先写好 O，再由 KR 来支撑。
4. **每个 O 配 3-5 个 KR，总量 3-5 个 O** — 多了等于没有优先级。KR 必须覆盖 O，不能有漏。
5. **60-70% 达成即成功** — 100% 达成说明目标太保守。OKR 是目标管理工具，不是 KPI 考核工具。
6. **OKR 不与薪酬/绩效直接挂钩** — 挂钩会导致目标保守化，失去挑战意义。

## 场景路由

收到用户请求后，先判断意图走哪个分支：

```
用户提到 OKR
  ├─ "制定/写/新季度/新年度" → 走「制定」流程
  ├─ "优化/改进/看看/诊断/有问题" → 走「优化」流程
  ├─ "评估/评分/复盘/季度末/年度末" → 走「复盘」流程
  └─ 意图不明确 → 问一句：你是在从零制定、优化已有的、还是做季度复盘？
```

### 走「制定」流程时

先确认两个关键信息（用户没说就问）：
- **周期**：月度、季度还是年度？（写法差异大，见上方「基础概念 → 月度 vs 季度 vs 年度 OKR」）
- **O 是否已有雏形**：如果用户完全没想法 → 先用场景构建法（`01-制定/05-场景构建法.md`）；如果有大致方向 → 直接用写作公式 + 解析法/验证法拆 KR

然后按 `01-制定/04-制定流程.md` 的 7 步法推进。每产出一组 OKR，跑一遍 `01-制定/06-常见错误.md` 末尾的判断清单自查。

### 走「优化」流程时

优化本质上是把「制定」的知识反过来用——诊断问题类型（见 `01-制定/06-常见错误.md` 的错误分类），然后逐条改写。若涉及多层级 OKR，检查对齐（见 `01-制定/04-制定流程.md` 末尾的对齐步骤）。

### 走「复盘」流程时

先确认周期（月度/季度/年度），然后：
- 逐条打分（0.0-1.0 评分：1.0=完美，0.7=良好达成甜点，0.3=有进展，0.0=未启动）
- 回顾 10 个维度：O 是否合理 / KR 是否覆盖 O / 量化标准是否合适 / 有无 KR 未覆盖的业务 / 进展顺利还是遇到问题 / 推进中的关键思考 / 对年度 OKR 的支撑 / OKR 之外的重要工作 / 意外收获或损失 / 对下周期的影响
- 提炼 Keep / Change / Stop / Start
- 输出复盘文档（模板见 `03-评分复盘/04-复盘输出模板.md`）
